# intel-overlord: VIctory on Intel Arc

A fork of [VIctory](https://github.com/Marvisak/VIctory) (through its AMD-tuned fork
VIctory-Belobug-AMD), a compatibility layer that runs an Xbox Series title natively on
Windows from files the user supplies, tuned here for **Intel Arc iGPU laptops that share
the PC's memory**. GPL-3.0, like its parents. **This repository contains no game files,
code or assets.** You need your own copy of the game; it is not affiliated with or endorsed
by the game's developer or publisher.

## Where it stands on Intel Arc (2026-11-27)

Tested on one machine: Windows 11, Core Ultra X9 388H, 31 GB of RAM, Arc B390 (driver
32.0.101.8724). Nothing here was measured on any other Intel part.

| | |
|---|---|
| Stays up | **yes, with mesh draws skipped (the default on Intel)**: 300 s in the world with no GPU hang, three memory profiles 220 s each |
| Speed in the world | about 125 to 136 ms a frame at the median (7 to 8 fps), 17 GB private, 1 to 2 GB of RAM left free at the end |
| Textures | stream within a budget taken from the PC's free RAM (the card's memory is the PC's memory); no hard cap, no waits on remaps |
| Shaders | the offline survey translates all 26,084 programs of the title; the driver built the pipelines the runs asked for, except 28 compute programs that need waves of 64, which this GPU (waves of 16 to 32) refuses |
| **Missing: the world's meshes** | the title's mesh draws stop this GPU (26 of 27 runs that issued them hung it, 56 to 147 s in, whichever shaders were drawn); the host skips them, so geometry drawn that way is not on screen: in one captured world frame 898 mesh draws were dropped against 34 vertex draws. The cause is not found. The textures that are drawn (loading art, title cards) are sharp; the scene itself has little left to texture |
| **Missing: some lighting and effects** | the 28 refused compute programs are GPU particles, decal trails, triangle-clip effects, volumetric water transmission, hair shadows and the `alphaResolve` mip prefilter; they are dropped every frame |

So: stable, but not a complete picture. Getting the meshes back is the open problem
(`docs/intel-arc.md` has 40 runs of experiments, what was ruled out, and the next steps);
making the 28 compute programs run in waves of 32 is translator work still to do.

### Run it

```powershell
cargo build --profile diag -p victory --features diagnostics
.\scripts\play-intel-lowmem.ps1 -Exe 'C:\path\to\game_scarlett_master.exe'
```

The launcher prints its settings, writes a log and a memory timeline to `logs\`, and
refuses to start under a free-RAM floor (`-MinFreeGB`). Profiles (`-Profile`, world
frames, 220 s each, one run each, so read the numbers loosely):

| Profile | Card buffers | Median frame | RAM left at the end |
|---|---|---|---|
| Lean | 128 MB | 545 ms | 1.8 GB |
| **Balanced** (default) | 512 MB | 136 ms | 2.1 GB |
| Fast | 1024 MB | 125 ms | 1.0 GB |

`-Capture` saves the presented frames as PNG files in `logs\frames-<time>\`, to see what is on screen.
If the title stays on "ACCOUNT PICKER / PLAYER", press Enter (the keyboard is the stand-in pad).
`-MeshTest off` draws the meshes anyway (the game then hangs the GPU within a minute or two).
`scripts\intel-sweep.ps1` runs the experiments one after another unattended and says which
settings survive; `scripts\intel-mesh-bisect.ps1` halves the mesh shaders by hash.

## Upstream notes: VIctory on an RX 7900 XTX

The rest of this file is the AMD fork's own README, kept as it was.

### The goal

**A stable 30 fps or more without ray tracing, then as high a frame rate and as
low frame times as the PC allows**, on an AMD RX 7900 XTX first and on PCs with
32 GB (later 16 GB) of RAM.

The way there is **porting, not emulating**: patching the title's renderer so it
behaves the way a PC renderer does, rather than having the layer watch and copy
the console's shared memory every frame. Shaders are translated ahead of time
into a versioned store that is kept between builds. Ray tracing stays optional
and off by default. The picture comes after the frame rate: texture pop-in and
lighting that is too bright or too dark when walking indoors are next in line.

**This repository contains no game files, code or assets.** You need your own
copy of the game. It is not affiliated with or endorsed by the game's developer
or publisher.

## Where it stands (2026-11-26)

Tested on one machine only: Windows 11, Intel i9-12900K, 64 GB RAM, Radeon
RX 7900 XTX, ray tracing off.

| | |
|---|---|
| City street, Series S profile, renderer patches 1, 2, 5, 6 and 7 on | about 45 ms a frame (about 22 fps, 44.9 ms in run merge-5) |
| Same, patches 1, 2, 5 and 6 | 45.6 ms, p95 47 ms |
| Same, patches 1, 2 and 5 | 47.3 ms (about 21 fps), p95 49 ms |
| Series X profile, patches 1+2 | about 53 ms (about 19 fps) |
| Same scene before the patches | 57-75 ms (13-17 fps) |
| Shaders the title uses that translate | all of them (25,790 of 25,985; the rest are unused geometry shaders) |
| Memory | about 30 GB of private memory, 10.5 GB of VRAM: **64 GB of RAM recommended** for now |

It started at 280 ms a frame in the same scenes three days earlier. What sets
the frame now is the one thread that submits the title's work to the card
(about 40 ms); the card itself needs about 36 ms and now waits about 7 ms a frame with nothing queued.

### Renderer patches (off by default while they are tested)

| Switch | What it does |
|---|---|
| `VICTORY_PORT_CONSTANTS=1` | The title's 174 MB constants heap is read by the card where the title writes it: no uploads, no fills |
| `VICTORY_PORT_DESCRIPTORS=1` | The title's descriptor-table stores are patched (byte-checked) to report the slots they write, instead of a scan of ~600,000 slots a frame |
| `VICTORY_PORT_CBV=1` | Translated shaders read constant buffers in place as raw bytes (~22,000 fills a frame to none; -4.7 ms) |
| `VICTORY_PORT_GUARD=1` | The write guards' lock is shared by faults and refreshes, with a claim per 64 KiB block; the submission's planning runs beside it (title threads' waits 29 ms to ~2 ms a frame; -2 ms) |
| `VICTORY_PORT_JOURNAL=1` | The heaps' records are asked for at the title's submit, and the journal's notes are split into 64 parts with locks of their own (the submit thread's waits ~5 ms + 1 ms to ~0.3 ms; -1 to -3 ms) |

### Other switches

| Switch | What it does |
|---|---|
| `--console series-s` | The Series S profile: 1080p output, about 5 ms faster, a softer picture |
| `VICTORY_OUTPUT=1920x1080` | The title renders to that output size itself (Series X profile; about 16 ms less card time) |
| `VICTORY_FRAME_INTERVAL_MS=16.667` | Lets the title go above 30 fps (menus and videos reach 60; the game's clock stays right) |
| `VICTORY_AMBIENT_SETTLE` | How fast light settles after walking indoors (on by default, `250,3`; `0` turns it off) |
| `VICTORY_TEXTURE_STORE=1` | Converted textures kept between runs (about 8 ms a frame for now: off) |

What is known to be wrong:

- Trees, signs and far objects flicker in the distance in some places.
- Lighting is too bright or too dark after walking indoors, until the title has
  run for a while; rooms with little direct light are too dark without `-RayTracing`.
- Textures of what just came into view appear late while the title streams.
- The first run of a new build stutters while the driver makes pipelines
  (`victory warm` makes them ahead).
- Recording a frame in the world makes the title's own watchdog end it.

## How to run it

You need Windows 10/11 x64, a CPU with AVX2, a Direct3D 12 GPU with shader
model 6.6 and mesh shaders, Rust (the toolchain is pinned), the MSVC build
tools, and your own dump of the title.

```powershell
git clone https://github.com/avatarmanz/VIctory-7900XTX
cd VIctory-7900XTX
copy victory.example.toml victory.toml      # then set your paths, outside this folder
cargo build --locked --profile diag -p victory --features diagnostics
scripts\play.ps1 -Exe <path of your copy's executable>
```

`scripts\play.ps1 -Safe` leaves out the newest, faster ways; try it first when
something is wrong. `-RayTracing` turns the title's ray-traced indirect light on.

For PC FSR 4.1.2, set `[paths].fidelityfx_dir` in `victory.toml` or
`VICTORY_FIDELITYFX_DIR` to the folder containing AMD's signed
`amd_fidelityfx_upscaler_dx12.dll`. Use the DirectX 12 upscaler in
`Kits/FidelityFX/signedbin`. [AMD FSR SDK 2.4.0](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/tree/v2.4.0/Kits/FidelityFX/signedbin)

`scripts\play.ps1 -Exe <path> -Fsr4K quality` selects 2560×1440 input for
the retail 1.0.2.1 Series X 4K SDR profile. `balanced` selects 2258×1270
and `performance` selects 1920×1080. All three output 3840×2160. With
`victory run` directly, set `VICTORY_FSR_4K` to the preset name.
The log reports the provider at context creation and the actual input and
output sizes at the first successful temporal dispatch. The title profile
and PC FidelityFX bridge were ported from [DexNom/VIctory](https://github.com/DexNom/VIctory/commit/ab34a8b21477c94da2a6cf07249138e8bc84602e).

On a hybrid-graphics PC, the runtime and offline pipeline checks prefer a
high-performance adapter with Shader Model 6.6. The runtime logs its adapter
name, PCI vendor and device IDs, and dedicated VRAM. Set
`VICTORY_D3D12_ADAPTER` to a zero-based DXGI index or part of the adapter's
name to select it explicitly. With the launcher, pass
`-More @{VICTORY_D3D12_ADAPTER='NVIDIA'}`.

Before the first run, ahead of time (both can be stopped and go on later):

```powershell
target\diag\victory.exe shaders <the shader archives>   # every shader translated, minutes
target\diag\victory.exe warm --used                     # pipelines earlier runs drew with, for a new driver or build
```

Intel Arc / shared-memory GPUs: [docs/intel-arc.md](docs/intel-arc.md).

Commands, debugging switches and upstream's own description:
[docs/README-fxceless.md](docs/README-fxceless.md). Every `VICTORY_...` switch is
described in a comment where it is read.

## What is different here

In short; the reasons and the measurements are in [docs/findings.md](docs/findings.md).

- **List calls are written down, not carried out, on the title's threads**
  (`VICTORY_THIN`): eight threads of ours translate them.
- **Submissions are prepared by a thread of ours and joined**
  (`VICTORY_ASYNC_SUBMIT`, `VICTORY_JOIN_PARTS`), with what can be spread over
  threads spread: refreshes, compares (AVX2), descriptor records, landings.
- **What shaders wrote comes back beside the write guards**, by the dwords that
  changed, on a thread of its own (`VICTORY_RELAY`, `VICTORY_LAND`).
- **Buffer fills that need bytes still on the card are done on the card**
  (`VICTORY_CARD_STEPS`) instead of waiting for it.
- **The title's writes are caught more cheaply**: one view opened at a fault,
  blocks that rest, places in the title's code that look before they write.
- **Textures go up on a copy queue of their own** and a slot shows one only after
  its upload ran, which also ended a device loss that came every 15 minutes or so.
- **Boats float**: textures that shaders write and the title's CPU reads go back
  to title memory (from fxceless and Geckomacabre, on by default here).
- **Frame record and replay** with per-pass times and shader variants compared
  turn by turn ([docs/replay.md](docs/replay.md)).
